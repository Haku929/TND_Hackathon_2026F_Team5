# 開発ルール

チームで開発するときの決まりごと。迷ったらここを見る。変えたいルールがあれば PR で提案する。

## 基本方針

- **`main` は常に動く状態に保つ。** 最終発表ではデモが必須なので、`main` を壊さないことを最優先にする。
- **作業はすべて Issue から始める。** 「誰が・何を・いつまでに」を GitHub 上で見えるようにしておく。
- **小さく作って早くマージする。** 1つの PR は 1 つの目的に絞り、目安として 1〜2 日以内にマージまで持っていく。

## 作業の流れ

1. Issue を作る（または既存の Issue を選ぶ）
2. 自分を Assignee に設定する
3. `main` から作業ブランチを切る
4. 実装してコミット・プッシュする
5. PR を作り、レビューを依頼する
6. 承認されたらマージし、ブランチを削除する

## Issue

- タイトルは「何をするか」が一目でわかるように書く（例：`ログイン画面を作る`）。
- 本文には **目的** と **完了条件** を書く。完了条件はチェックリストにすると進捗が見やすい。
- 着手前に Assignee を設定する。手が止まったら Assignee を外すか、Issue にコメントで状況を残す。
- ラベルで種類を分ける。

| ラベル | 用途 |
| --- | --- |
| `feature` | 新機能 |
| `bug` | 不具合 |
| `docs` | ドキュメント・README・スライド |
| `security` | セキュリティ対策・テスト |
| `chore` | 環境構築・設定・リファクタリングなど |

## ブランチ

- `main` に直接プッシュしない。必ず PR を経由する。
- ブランチ名は `<種類>/<Issue番号>-<内容>` にする。種類はラベルと同じ。

```
feature/12-login-page
bug/18-fix-submit-error
docs/5-update-readme
```

- マージ済みのブランチは削除する。
- 作業中に `main` が進んだら、こまめに `main` を取り込んでコンフリクトを小さく保つ。

## コミット

- 1 コミット 1 変更を意識する。「ついでの修正」は別コミットに分ける。
- メッセージは次の形式にする。日本語でも英語でもよい。

```
<種類>: <変更内容の要約>
```

| 種類 | 用途 |
| --- | --- |
| `feat` | 機能追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメント |
| `style` | 見た目・フォーマットのみの変更（動作に影響しない） |
| `refactor` | 動作を変えないコード整理 |
| `test` | テストの追加・修正 |
| `chore` | 設定・依存関係・ビルドまわり |

```
feat: ログイン画面を追加
fix: 送信ボタンを連打すると二重登録される問題を修正
```

## Pull Request

- タイトルはコミットと同じ形式にする。
- 本文に関連 Issue を `Closes #12` の形で書く（マージ時に Issue が自動で閉じる）。
- 本文には次を書く。
  - **何を変えたか**
  - **動作確認の方法**（画面の変更ならスクリーンショットを貼る）
- 作業途中で意見がほしいときは Draft PR で出してよい。

## レビュー

- マージには **1 人以上の承認** が必要。自分の PR を自分でマージするのは、承認をもらってからにする。
- レビュー依頼を受けたら、できるだけ **24 時間以内** に反応する。すぐ見られないときは一言コメントを残す。
- 指摘には必須と任意を区別して書く。任意の指摘は先頭に `[nits]` を付ける。
- 責めるのではなくコードについて話す。「なぜこうしたのか」を聞くのは歓迎。

## 秘密情報の扱い

秘密情報の流出は事故につながる。

- API キー・パスワード・トークンを **コミットしない**。`.env` に書き、`.env` は `.gitignore` に入れる。
- 必要な環境変数は `.env.example` に **キー名だけ** 書いて共有する。実際の値はチャンネルの DM などリポジトリ外で渡す。
- うっかりコミットした場合は、すぐにチームに報告し、そのキーを **無効化して再発行** する（履歴から消すだけでは不十分）。

## セキュリティ対策の記録

セキュリティは独立した審査項目なので、対策とテストの記録を残す。

- 対策を入れたら Issue / PR に `security` ラベルを付ける。
- どんな攻撃を想定し、どう対策し、どうテストしたかを README の「セキュリティ対策」の表に追記する。

## AI ツールの利用

- Claude Code・Copilot などのコーディング支援 AI は自由に使ってよい。
- ただし **自分が説明できないコードはコミットしない。** レビューで質問されたら答えられる状態にしておく。
- 生成されたコードに秘密情報やライセンス上問題のあるコードが含まれていないか確認する。

## コミュニケーション

- 連絡はチームのチャンネルで行い、議事録などの資料は共有ドライブに置く（リンクは README 参照）。
- 作業の相談・決定事項は、できるだけ Issue / PR のコメントにも残す。チャットだけで決めたことは後から追えない。
- 詰まったら 30 分を目安に誰かに相談する。抱え込まない。

## 未決事項

技術スタックが決まったら追記する。

- [ ] コードフォーマッタ・リンタ（例：Prettier / ESLint）と設定
- [ ] ディレクトリ構成
- [ ] テストの方針（どこまで書くか）
- [ ] デプロイ先と手順
