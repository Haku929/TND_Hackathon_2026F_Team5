# KAKEN API の使い方

先生と研究テーマのデータを KAKEN から取得するときの手引き。担当は #4（キー取得）、#5（規約）、データ取得の Issue 群。

> **確認の状態:** パラメータの仕様は NII 公開の定義書（[kaken_definition](https://bitbucket.org/niijp/kaken_definition/src/master/) の `KAKEN_API_parameters_document_Ja`）による。**実際に API を叩いて確かめた項目には「確認済」、まだの項目には「未確認」と書く。** 確かめたら書き換える。

## 1. 最初に守ること

- **API キー（appid）はリポジトリに書かない。** `.env` に `KAKEN_APPID=...` として置き、`.gitignore` に入れる。チャットやコメントにも貼らない。
- キーを他人に貸さない（利用細則 第5条）。使うのはデータ取得スクリプトを動かす人だけにする。
- **短時間に大量のアクセスをしない**（利用細則 第6条）。リクエストの間隔を空ける（目安: 1 秒に 1 回以下）。アプリの実行中には叩かず、**事前に取得して自前に保存**する。
- 取得結果を表示するときは、出典と加工した旨を載せる（DESIGN.md 10 章）。

規約の詳細は #4 と #5 のコメントを参照。

## 2. エンドポイント

| 何を探すか | URL |
| --- | --- |
| 研究課題（どんな研究か） | `https://kaken.nii.ac.jp/opensearch/` |
| 研究者（誰か） | `https://nrid.nii.ac.jp/opensearch/` |

すべてのリクエストに `appid=<キー>` が要る。キーなし・不正なキーはどちらも 403 になる（確認済。キーなしは `Exceeds allowed rate`、不正なキーは `Invalid APPID`）。

## 3. 共通のパラメータ

| パラメータ | 意味 | 備考 |
| --- | --- | --- |
| `appid` | API キー | 必須 |
| `kw` | フリーワード | URL エンコードする。ほかの検索条件を指定しないなら必須 |
| `rw` | 1 ページの件数 | 20, 50, 100, 200, 500 から選ぶ。既定は 20 |
| `st` | 取得の開始番号 | 既定は 1。ページ送りに使う |
| `lang` | 結果の言語 | `ja`（既定）か `en` |
| `format` | 返す形式 | **下の注意を参照** |
| `od` | 並び順 | 研究課題と研究者で値の意味が違う |

### 返す形式（`format`）は 2 つの API で違う

| API | 指定できる形式 | 既定 |
| --- | --- | --- |
| 研究課題 | `html5`, **`xml`** | html5 |
| 研究者 | `html5`, **`json`** | html5 |

- 指定を省略すると**画面用の HTML が返る**。必ず指定する。
- 研究課題の API に `format=json` は使えない。
- 別形式の定義書: [KAKEN_XML_definition](https://bitbucket.org/niijp/kaken_definition/src/master/)（課題の XML の項目）、`KAKEN_researcher_JSON_definition`（研究者の JSON の項目）。

### 取得できる件数の上限

| API | `st` の上限 |
| --- | --- |
| 研究課題 | 200,000 件 |
| 研究者 | **1,000 件** |

研究者検索の制約は**開始位置 `st` の上限が1,000**というもの。「取得できるレコードが先頭1,000件だけ」とは異なる。2026-11-05に `st=1000`、`rw=20` で20人が返ることを確認した。全件取得では複数の並び順や検索条件を使い、研究者番号で重複を除いた件数を `totalResults` と照合する。先頭のページだけで全件取得できたとは判断しない。

## 4. 研究課題の検索（`kaken.nii.ac.jp/opensearch/`）

| パラメータ | 絞り込む項目 | 補足 |
| --- | --- | --- |
| `qa` | 研究課題名 | URL エンコード |
| `qb` | 研究課題番号 | |
| `qc` | 研究種目 | URL エンコード |
| `qd` | 審査区分／研究分野 | URL エンコード。**30 分野との対応表の元データ**（DESIGN.md 11 章） |
| `qe` | 研究機関 | 立命館大学で絞るときに使う |
| `qf` | キーワード | |
| `qg` | 研究者の姓名 | |
| `qh` | 研究者の所属機関 | |
| `qm` | 研究者番号 | |
| `s1`, `s2` | 助成期間の開始・終了年度（From, To） | 数字のみ。From > To はエラー |
| `o1` | 期間の判定方法 | 1=開始年度, 2=終了年度, 3=期間の一部を含む, 4=期間の全部を含む |
| `c1` | ステータス | 複数指定可。例: `adopted`（採択）, `project_closed`（完了） |
| `c2` | 研究者の役割 | 複数指定可。例: `principal_investigator`（研究代表者） |
| `c6` | 課題の種別 | 複数指定可。例: `project`（研究課題） |
| `od` | 並び順 | 1=適合度, 2=開始年が新しい順（既定）, 3=古い順, 4=配分額が多い順, 5=少ない順 |

ほかに、配分額 (`s3`)、報告書の種類 (`c3`)、評価 (`s4`, `s5`)、成果の種別 (`c5`) などがある。全項目は定義書を参照。

## 5. 研究者の検索（`nrid.nii.ac.jp/opensearch/`）

| パラメータ | 絞り込む項目 |
| --- | --- |
| `qg` | 研究者の姓名 |
| `qm` | 研究者番号 |
| `qh` | 所属機関 |
| `qq` | 部局 |
| `qs` | 職名 |
| `qa`, `qb`, `qc`, `qd`, `qe`, `qf` | 研究課題名・番号・研究種目・審査区分・研究機関・キーワード（課題側の条件） |
| `s1`, `s2`, `o1` | 研究期間（年度）。研究課題側と同じ意味 |
| `od` | 並び順。1=適合度, 2〜3=カナ順（昇順・降順）, 4〜5=アルファベット順, 6=課題数が少ない順, 7=課題数が多い順（既定） |

## 6. 検索条件の書き方（`kw` などに入れる文字列）

- 空白で区切ると AND。大文字の `OR`、`NOT` も使える。括弧は使えない。
- `"..."` で囲むとフレーズ検索。
- 末尾に `*` で前方一致。後方一致・中間一致はできない。
- 人名は、姓と名の間にスペースを入れずに入れると完全一致する（例: `山田一`）。
- 日本語は URL エンコードが必要。

## 7. リクエスト例

> キー部分は `$KAKEN_APPID` とする。実行前に環境変数へ入れる。

**立命館大学の研究課題を 1 ページ分、XML で取る**

```bash
curl -s "https://kaken.nii.ac.jp/opensearch/?appid=$KAKEN_APPID&qe=%E7%AB%8B%E5%91%BD%E9%A4%A8%E5%A4%A7%E5%AD%A6&format=xml&rw=100&st=1"
```

**立命館大学の研究者を JSON で取る（先頭 100 件）**

```bash
curl -s "https://nrid.nii.ac.jp/opensearch/?appid=$KAKEN_APPID&qh=%E7%AB%8B%E5%91%BD%E9%A4%A8%E5%A4%A7%E5%AD%A6&format=json&rw=100&st=1"
```

認証付きのXML・JSON応答は確認済み（2026-11-02、各20件）。課題の `qe` は試した20件すべてで日本語summaryの研究機関に立命館大学を含んだ。一方、研究者の `qh` は過去の所属も含み、試した20人のうち現在所属に立命館大学を含んだのは13人だった。現在所属の研究者だけを使う場合は、取得後に `affiliations:current` の機関名が「立命館大学」と完全一致する記録を選ぶ。部局の `qq` も現在の部局を保証しない。

## 8. データ取得スクリプトの方針

1. キーは環境変数 `KAKEN_APPID` から読む。
2. リクエストの間隔を空ける（1 秒以上）。403 や 429 が返ったら待って再試行する。連続して失敗したら止める。
3. 研究者は開始位置 `st` の上限に注意し、並び順や検索条件を組み合わせて取得する。研究者番号で重複を除き、検索総件数と照合する。現在所属は `affiliations:current` で確認し、課題実施当時の所属と区別する。
4. 取得した生データは `data/` 配下のローカル（`.gitignore` 対象）に置く。**生データはリポジトリに入れない**（DESIGN.md 10 章）。
5. リポジトリに入れるのは、アプリに必要な最小限の加工済みデータだけにする。

### 取得・整理スクリプト（#21）

`data/fetch_kaken.py` をPython 3.10以上で実行する。追加パッケージは不要。キーは環境変数 `KAKEN_APPID` を優先し、未設定ならリポジトリ直下の `.env` にある同名の値を読む。キーやキー入りURLは表示・保存しない。

```powershell
python data/fetch_kaken.py
npx prettier --write data/researchers.json
```

- 研究者検索で現在所属を照合し、研究課題検索で `qe=立命館大学` に一致する課題を取得する。現在所属の機関名が「立命館大学」と完全一致する人だけを整理する。
- 課題の対象は立命館大学で実施された課題であり、現在の所属者が他大学で実施した全課題まで網羅するものではない。
- API応答と取得条件・件数・ハッシュは `data/raw/` に保存する。保存済みページを再利用し、欠損・改変・件数不一致を検出したら停止する。`data/raw/` はGit管理の対象外。
- 整理結果は `data/researchers.json` に保存する。研究者番号・名前・現在所属・URL・テーマ文章と、参画課題の題名・キーワード・概要・審査区分／旧研究分野・課題当時の所属・役割を保持する。テーマは原文の連結で、LLMによる要約・翻訳は行わない。
- 採択後辞退（`declined`）や課題名のない課題はテーマ作成から除外する。キーワード・概要の欠損は補作せず、件数を記録する。分野の割り当てと埋め込み計算は後続の#22・#23で行う。

概要はAPIの項目を利用し、報告書PDFの全文は取得・利用しない。研究開始時の概要、成果・実績の概要、単に `abstract` とされた研究概要は区別できるが、この種類の分類自体は利用許諾の判定ではない。概要の一律削除は行わず、著作物と明示された一部の旧報告書等の例外は別途確認する。個別の著作権表示・利用条件の照合は未完了であり、APIから取得できることだけで共有・再利用可能と保証しない。

保存済みデータだけで再整理する場合は `python data/fetch_kaken.py --offline`。所属照合だけを先に確認する場合は `python data/fetch_kaken.py --nrid-only` を使う。研究者検索は複数の並び順を併用し、重複除去した研究者番号の総数をAPIの `totalResults` と照合する。取得しきれない場合は部分的な結果を完成品として保存しない。

通信なしのテスト:

```powershell
python -m unittest discover -s data -p test_fetch_kaken.py -v
```

## 9. 未確認の項目（実際に叩いて確かめる）

- [x] キーを使った正常系のレスポンス（`format=xml` / `format=json`）: 両方でHTTP 200と解析成功を確認（2026-11-02）。
- [x] `qe` / `qh` への `立命館大学` の指定で、検索結果を取りこぼさず取得できるか: 2026-11-05に課題5,860件、研究者検索の2,925人を取得し、IDの重複除去後の件数がそれぞれAPIの総件数と一致した。研究者検索には過去所属者も含まれるので、現在所属を確認してから使用する。大学の全教員やKAKEN未登録者の網羅性を示すものではない。
- [x] 研究者の総数と取得上限への対応: 研究者検索は2,925人。氏名カナの昇順・降順だけでは2,850人、アルファベット順も加えると2,923人だった。課題数の少ない順の1ページを補って2,925人に一致した。使用した並び順は `od=2,3,4,5,6`、各ページの件数は500、開始位置は1・501・1000（`od=6` は1のみ）。最大6種類の並び順でも総件数に届かない場合は条件分割が必要として停止し、不完全なデータを完成品にしない。
- [ ] 1 回あたりの実際のレート制限（何回目で403になるか）: 上限を探る連続アクセスは行わない。利用細則に沿ってリクエスト間隔を空け、通常取得時の応答とエラー処理を記録する。
- [x] 研究者のJSONと課題のXMLに必要項目があること: JSONは `id:person:erad`、`name`、`affiliations:current`、`work:project` に番号・名前・現在所属・参画課題がある。XMLは課題名・キーワード・概要・審査区分・研究者番号・課題当時の所属を持つ。ただし項目の欠損があり、全記録ですべて揃うわけではない。

### #21 取得・整理の結果（2026-11-05）

| 項目 | 件数 |
| --- | ---: |
| `qe=立命館大学` の研究課題 | 5,860 |
| `qh=立命館大学` の研究者（過去所属を含む） | 2,925 |
| APIの現在所属が立命館大学の研究者 | 1,407 |
| 対象課題への参画を確認でき、JSONに収録した研究者 | 1,201 |
| 収録した研究者が参画した課題（重複除去後） | 3,374 |
| 研究者と課題の組み合わせ | 4,332 |

現在所属の1,407人のうち206人は、今回取得した課題への有効な参画記録がなく、収録対象外。全取得課題のうち採択後辞退46件はテーマ作成から除外した。全課題では題名の欠損0件、キーワードの欠損371件、概要の欠損329件。収録対象の3,374課題ではキーワードの欠損5件、概要の欠損1件だった。

課題の研究者記録を除外した件数は、現在所属が他機関5,977件、現在所属不明6,170件、研究者番号なし1,273件、研究者APIに対応する記録なし10,794件。これは延べ参画記録数で、研究者数ではない。206人の未収録も含め、`coverage.grouping` に理由と件数を保存している。

本取得では研究者13ページ・研究課題12ページの計25ページがHTTP 200。リクエスト間隔は1.05秒以上とし、403・429では10秒待って1度だけ再試行する。実際の制限回数を探る負荷試験は行っていない。保存済みキャッシュだけの `--offline` 実行でJSON生成にも成功した。

8件の通信なしテストで、XMLの実際の研究者番号・入れ子の所属・英語フォールバック・旧研究分野、現在所属の選別、最終ページ、キャッシュ破損、取得漏れ、エラー時のキー非表示と再試行上限を確認した。生成JSONの全1,201人がAPIの現在所属条件を満たし、課題名・キーワード・概要・審査区分・旧研究分野が取得データと一致することも検証した。キー混入チェックは通過し、`data/raw/` がGit対象外であることを確認済み。`npm run lint` と `npm run format:check` も成功した。

テーマはすべての参画課題を連結するため長文になる場合がある（最大17,103文字）。#23でモデルの入力長と扱う課題の順序を検討する。今回の取得処理では埋め込み計算や分野の割り当てを行っていない。
